# Upgrading GLPI under glpi-inv — what breaks, in what order

Everything `glpi-inv` knows about GLPI was verified against **11.0.12** and
much of it is version-specific. This file is the inventory of that coupling:
what an upgrade can break, which failures are loud and which are quiet, and
what to check first.

Written because the couplings were each recorded where they were discovered -
`gl-rights.md`, `gl-db-api.md`, `gl-sql-plan.md` - and nobody had collected
them. Column lists and call lists below were read out of the code and the GLPI
source, not remembered.

- **Biggest exposure:** the v1 API, which GLPI promises nothing about — though
  for 12.0.1 specifically it survives
- **Loudest failures:** anything the API refuses or truncates — these shout
- **Quietest failure:** a renamed database column — a blank cell, no error
- **Cheapest insurance:** read the four checks at the end before upgrading

---

## 1. The v1 API — the one that could stop the app dead

Five of the app's calls have **no v2.3 equivalent at all**:

| v1 call | what dies without it |
|---|---|
| `ProfileRight` | every right on the Rights page, all nine profiles |
| `Profile` | the profile list it groups them under |
| `Profile_User` | the whole Authorizations table |
| `Entity` | entity names in Authorizations |
| `getFullSession` | which account the app is |

GLPI's own description of v1, served at `/api.php`:

> *"The low-level API which is closely tied to the GLPI source code… It has no
> promise of stability between versions so it may change without warning."*

**A major version is exactly where a deprecated API gets removed.** v2.0, v2.1
and v2.2 are already flagged `"deprecated": true`; v1 is not flagged but is
described as unstable, which is worse in practice.

If v1 goes, the Rights page loses its data source and there is no fallback -
the whole reason the app speaks two APIs is that v2.3 cannot answer these.
Mitigation is not a code change: it is checking, before upgrading, whether the
new version still serves `/apirest.php/ProfileRight`.

**For 12.0.1 that check is already done and the answer is yes.** `API.php`,
`APIRest.php` and the `Deprecated/` directory all exist at that tag, and
`Router.php` serves three HL versions — 1, 2.3 and 3.0 — with none flagged
deprecated. The check stays first for any *future* version; it is not an open
question for this one.

**Fails loudly.** A removed endpoint is a 404 and the page says so.

## 2. The HL API version string

`backend/src/glpi/mod.rs:229` builds every v2.3 URL from one literal:

```rust
format!("{}/api.php/v2.3/{}", self.base, path)
```

A GLPI that drops v2.3 or introduces v3 needs that one line changed, and then
every schema below re-checked. `/api.php` lists what a given install actually
serves - read it first rather than assuming.

The five v2.3 paths, all of which must still exist:

```
Inventory/Agent        Assets/Computer        Administration/Entity
Administration/User    session
```

**Fails loudly.** Wrong version in the path is a 404.

## 3. The pagination contract

The client walks collections with `start`/`limit` until the served window
reaches the total, reading `Content-Range: start-end/total` and treating 206 as
"more remain". Measured on 11.0.12:

```
Assets/Software                       ->  206  Content-Range: 0-99/1330
Assets/Software?limit=500             ->  206  Content-Range: 0-499/1330
Assets/Software?start=1300&limit=100  ->  200  Content-Range: 1300-1329/1330
```

Three assumptions here, any of which an upgrade could move: the parameter
names, the header format, and 206-versus-200 marking the end.

**Fails loudly, by construction.** The walk refuses rather than guesses on a
header it cannot parse, a page that returns nothing while claiming more exist,
and a multi-page collection that is not an array. That was deliberate: a short
list presented as a complete one is the worst answer this app can give.

## 4. The right names

Five, and the app is useless without them:

```
agent   computer   entity   profile   user
```

These are `static::$rightname` on the class behind each endpoint - PHP, not
data, so an upgrade can rename one. `Agent::$rightname` already carries a
commented-out alternative (`inventory`) directly beneath the live value, which
is upstream's own abandoned rename sitting in the file.

**Fails loudly.** A renamed right reads as 403, and the Rights page's Api tab
names which call was refused and which right it wanted.

## 5. The right taxonomy

`backend/src/glpi/right_taxonomy.json` is a committed copy of
`Profile::getRightsForForm()`, regenerated by `just right-taxonomy`. An
upgrade that adds, moves or renames a right leaves the copy stale.

**Fails visibly, not loudly.** A right the copy cannot place appears under
*Not on the profile form* on the Rights page, which is also where genuinely
unlistable rights live - so a growing bucket is the signal. Re-run the recipe.

Two kinds never move from that bucket however often it is re-run, and that is
not drift: inactive custom asset types (`getDefinitions(only_active: true)`)
and all custom dropdown types, which `getRightsForForm` never adds. See
`gl-db-api.md`.

## 6. The database schema — the only quiet failure

The app reads **12 of the 14** columns of `glpi_refusedequipments`:
(The grant was SELECT on two tables when this was written and is now
server-wide, which widens nothing here: the coupling below is to the columns
this code names, and that list is unchanged.)

```
read:     id  name  itemtype  entities_id  ip  mac  rules_id  method
          serial  uuid  agents_id  date_creation
not read: date_mod  autoupdatesystems_id
```

`glpi_logs` is granted and **read by nothing** - 12 columns, zero used. An
upgrade cannot break what nothing reads, but the grant is wider than the code
and that is worth revisiting independently.

**This is the quiet one.** An API that drops a field names the field; SQL does
not. A renamed column makes the query fail; a column that changes meaning makes
it succeed and lie. Every column is treated as optional and renders blank, so
the failure mode on screen is a gap, not an error.

The Rights page's **Db tab** and the DB page's **Schema tab** exist to make
this comparable against a release - that is their whole purpose.

## 7. Configuration keys

Four `glpi-console config:set` keys the app depends on:

```
enable_api                    enable_hlapi
enable_api_login_credentials  url_base_api
```

`enable_api_login_credentials` is needed only for v1's Basic-auth sign-in, so
it shares the fate of section 1. `url_base_api` is the one GLPI gets wrong by
default on a non-80 port - see `docs/oauth-setup.md` in the repo.

**Fails loudly**, but misleadingly: a disabled API reads as an auth failure
rather than as a switched-off feature.

## 8. OAuth

The `password` grant, not `client_credentials` - `Router.php:717` requires a
logged-in user and a client-only token has none. The OAuth client needs the
`api` scope. Both are install configuration rather than code, so an upgrade
affects them only if GLPI changes its grant handling.

## Four checks, before upgrading

In this order, because the first answers whether the rest matters:

1. **`GET /apirest.php/ProfileRight`** — does v1 still exist? If not, stop and
   decide what the Rights page becomes before upgrading anything.
2. **`GET /api.php`** — which versions does the new install serve? If v2.3 is
   gone, `mod.rs:229` and all five paths in section 2 need re-checking.
3. **`just right-taxonomy`** — regenerate, and read the diff. It is the
   cheapest signal that rights moved.
4. **`just gate-rust`, then open the Rights and DB pages.** Both were built to
   state what they cannot see, so a changed upstream shows up as a named gap
   rather than as a blank.

## Upstream's own procedure, and how little of it applies here

From GLPI's install documentation (`glpi-install.readthedocs.io`, update page):
back up, **move or delete the old installation directory**, extract the new
release in its place, restore `config`, `files`, `plugins`, `marketplace` and
`inc/downstream.php`, then migrate the database.

Most of that is already structural on this install, which is worth knowing
before anyone follows the generic instructions:

| upstream step | here |
|---|---|
| "Move or delete the existing directory — copying the new release over an existing installation can cause application errors" | **impossible to get wrong.** The source is an immutable `/nix/store` path; a new version is a new path. Nothing is ever copied over anything. |
| Preserve `config`, `files`, `marketplace` | **already outside the release.** `glpi.nix:147-149` points `GLPI_CONFIG_DIR`, `GLPI_VAR_DIR` and `GLPI_MARKETPLACE_DIR` at `/var/lib/glpi/*`, and the `glpi-console` wrapper exports the same three. |
| Preserve `plugins`, `inc/downstream.php` | nothing to preserve — no plugins are installed, and `plugins/` in the release is empty. |
| Back up the database | **still entirely manual.** Nix does nothing for this. |

So the file-shuffling half of upstream's procedure reduces to editing two lines
in `glpi.nix` — `version` and `hash` — and rebuilding. What remains is the
database migration, which Nix cannot do for you.

### The migration commands

Verified against 11.0.12 rather than taken from the "latest" docs, because the
documented names are aliases and aliases move. Canonical names first:

```sh
sudo -u glpi glpi-console database:check_schema_integrity   # alias: db:check
sudo -u glpi glpi-console database:update                   # alias: db:update
sudo -u glpi glpi-console database:is_up_to_date            # alias: db:is_up_to_date
```

`sudo -u glpi` because the console needs to read `config/`, and the wrapper
already exports the three directory variables. `plugin:resume_execution` is
documented as needed after a major update on 11.0+ and exists here, but there
are no plugins to resume.

### One useful thing it does say

> "GLPI 11 contains the necessary migrations for version 0.85 and greater, so
> it is possible to skip even major versions entirely if necessary."

So being several versions behind is not itself a blocker, and there is no need
to step through intermediate releases.

### And one thing it does not say

**The update documentation says nothing about API compatibility, deprecated
APIs, or which API versions a release serves.** So section 1 above — whether
v1 survives — is not answered anywhere upstream tells you to look. It has to
be checked against the new release directly, which is why it is the first of
the four checks below rather than something to read about.

## Upgrading to 12.0.1 — the specific case

The sections above are the general inventory. This one is the plan for the
version actually on the table, and it begins by settling the question the
inventory left open.

**Not done. This is a proposal.**

- **The feared blocker does not exist** — v1 survives in 12.0.1 — verified
- **v2.3 also survives**, so the client's pinned path still resolves — verified
- **The prize:** HL API **v3.0.0** is new, and might expose what v1 and SQL are
  currently used for — unverified, and the main thing to find out
- **No urgency:** 11.0.12 is current on a maintained branch

### What I verified in the 12.0.1 source

| claim | finding |
|---|---|
| the legacy v1 API is removed | **false.** `src/Glpi/Api/API.php`, `APIRest.php` and the `Deprecated/` directory all still exist at tag 12.0.1 |
| which HL versions are served | `Router.php` declares **three**: `1` (1.0.0), `2` (2.3.0), `3` (3.0.0) |
| are any marked deprecated | **none are.** The v2.0/2.1/2.2 entries that 11.0.12 flagged as deprecated are simply gone; v2 is now represented by 2.3.0 alone |
| `Session::changeProfile` trap | **unchanged.** `GLPI-Profile` is still handled by calling `changeProfile`, which is still a silent no-op for an unauthorised profile — so the guard in `glpi/rights.rs` is still required |

#### Correcting section 1 above

Section 1 calls the v1 API "the one that could stop the app dead" and makes
checking its survival the first pre-upgrade step. The check still belongs
first, but the answer for 12.0.1 is already known and it is *yes, it
survives*. The five calls with no v2.3 equivalent — `ProfileRight`, `Profile`,
`Profile_User`, `Entity`, `getFullSession` — should keep working.

A changelog summary did claim the legacy REST API was removed in 12.0. That was
an inference from the API section having been rewritten; the only API item
actually in the Removed list is **XML-RPC**, which this app never used. Checking
the source tree is what settled it, and is the reason this plan is not built on
that claim.

### The prize: does v3 make v1 and the SQL grant unnecessary?

This is the question worth upgrading *for*, and it is unanswered. The app
reaches outside v2.3 in exactly two places, both documented as "the API cannot
do this":

- **v1**, for `ProfileRight`, `Profile`, `Profile_User`, `Entity`,
  `getFullSession` — the Rights page and the Authorizations table
- **SQL**, for `glpi_refusedequipments` — the refused view, with
  `glpi_logs` granted but unused

If v3.0.0 exposes profile rights, profile-user authorizations, or refused
equipment, then upgrading lets the app **drop a whole second API client and
possibly the database grant entirely** — removing the schema coupling that is
its only quiet failure mode, and the second authentication path with it.

That is a large simplification, and it is the thing to test first. It is also
entirely speculative until tested: v3 being new says nothing about what it
covers.

**Tested, and the answer is no.** v3 exposes none of the three. See *Phase 3,
run* below for what was read; the consequence is that phase 6 is off and the
app keeps both the second API client and the grant.

### Known changes that touch this app

| change in 12.0 | effect here |
|---|---|
| `KnowbaseItemCategory` itemtype and the **`knowbasecategory` right removed** | a right name disappears. The Rights page reads names live so it adapts by itself, but the committed taxonomy copy will carry a stale entry — which surfaces in the *form-only rights* line rather than silently |
| CSRF protection replaced with browser-native header validation | affects GLPI's own UI, not an API client using a bearer token. Worth confirming it does not touch the OAuth flow |
| XML-RPC API removed | never used |
| HL API v3.0.0 added | see above |
| PHP requirement | **unknown.** The changelog does not state it, and it decides whether the Nix build needs a newer PHP than the 8.4.27 currently used |

### The plan

Six phases. Nothing touches the live install until phase 5.

#### Phase 0 — decide whether to go at all

11.0.12 is current on a maintained branch, so there is no security pressure.
The reasons to move are the v3 simplification above and branch longevity —
10.0.28 was announced as the final 10.0 release, so branches do get retired.
If v3 turns out to cover nothing this app needs, deferring is defensible.

#### Phase 1 — build it, deploy nothing

In `glpi.nix`, change `version` to `12.0.1` and let the hash mismatch report
the real hash. Then build only:

```sh
nix build .#glpi            # or whatever attribute the flake exposes
```

Resolves two things cheaply: whether it builds at all, and the PHP
requirement. Do not switch.

#### Phase 2 — a throwaway instance on a copy of the database

Never the live database. Dump it, load the copy into a scratch schema, point a
second instance at that, and migrate:

```sh
sudo -u glpi glpi-console database:check_schema_integrity   # before
sudo -u glpi glpi-console database:update
sudo -u glpi glpi-console database:is_up_to_date
```

Per upstream, GLPI 11 carries migrations from 0.85 up, so 11.0.12 → 12.0.1 is
within the supported path and no intermediate release is needed.

#### Phase 3 — probe the APIs, which is the real test

Against the test instance, in this order:

1. `GET /api.php` — confirm it serves 1, 2.3 and 3, and read what it says
   about each.
2. The **five v1 calls**. If any fails, the Rights page and Authorizations
   table lose their source and the upgrade stops being routine.
3. The **five v2.3 paths**: `Inventory/Agent`, `Assets/Computer`,
   `Administration/Entity`, `Administration/User`, `session`.
4. **v3, for the three things currently unreachable** — profile rights,
   profile-user authorizations, refused equipment. This is the phase that
   decides whether the upgrade is a simplification or just a version bump.
5. Re-check the **pagination contract**: parameter names, `Content-Range`
   format, and 206-versus-200 marking the end. The client walks collections on
   those three assumptions.

`just probe <path>` runs against whatever `GLPI_URL` points at, so it can test
the instance without touching app code.

#### Phase 4 — the app against the test instance

```sh
just right-taxonomy      # regenerate; read the diff
just gate-rust           # 67 tests
```

Then open each page and read what it reports rather than assuming silence
means success. Both the Rights and DB pages were built to state what they
cannot see, so a changed upstream should surface as a named gap:

- a right that moved → *Not on the profile form*
- a right that vanished → the form-only line
- a dropped v2.3 field → a blank cell, not an error
- a refused call → the Api tab names it and the right it wanted

Check the **DB page's Schema tab** against 12's install SQL for
`glpi_refusedequipments` and `glpi_logs`. This is the only coupling that fails
quietly, so it is the only one that needs reading rather than watching.

#### Phase 5 — the real upgrade

Database backup first; Nix does nothing for that. Then the version bump,
rebuild, `database:update`, and restart `glpi-inv`.

Rollback is asymmetric and worth being clear-eyed about: **the Nix side rolls
back cleanly** — the old store path still exists, so reverting `glpi.nix` and
rebuilding restores the old code exactly. **The database does not.**
`database:update` migrates the schema forward, so rolling back means restoring
the dump. That makes the backup the actual rollback plan, not a formality.

#### Phase 6 — if v3 delivers

Only if phase 3 found v3 covers what v1 and SQL are used for:

- move those calls to v3 and delete `glpi/legacy.rs` and its session handling
- if refused equipment is exposed, delete `glpi/refused.rs`, drop
  `mysql_async`, and **revoke the grant** — which removes the schema coupling,
  the second auth path, and the one failure mode that is silent
- update `gl-sql-plan.md` to record that the trade it proposed was superseded

That would leave the app speaking exactly one API, which is what it wanted to
do from the start.


### Phase 3, run — the answer is no, and that settles phase 6

Run on 2026-11-04, against the live 11.0.12 install for the baseline and
against the **12.0.1 release tarball** for everything about the new version.
No test instance exists yet: phases 1 and 2 have not been run, so the half of
phase 3 that needs a migrated database is still outstanding. What follows is
the half that does not.

Source read from the release tarball this time, not from GitHub:
`sha256-v4mhvkDqduTnpqXOqP0kydgi+rg+TpBRn/DI0GLxMpE=`, carrying a
`version/12.0.1` marker.

#### Step 4 first, because it decides what the upgrade is for

**v3.0.0 exposes none of the three things that are currently unreachable.**

| needed outside v2.3 | occurrences under `src/Glpi/Api/HL/` in 12.0.1 |
|---|---|
| `Profile_User` — the Authorizations table | **0**, unchanged from 11.0.12 |
| `RefusedEquipment` — the refused view | **0**, unchanged from 11.0.12 |
| profile rights across profiles | **not modelled.** The HL `Profile` schema carries the same eight properties as 11.0.12 — `id`, `name`, `comment`, `is_default`, `helpdesk_hardware`, `helpdesk_item_type`, `managed_domainrecordtypes`, `mfa_enforced`. No rights, no `interface`, and nothing on it is `x-version-introduced: 3.0` |

`ProfileRight` does appear under HL, three times, and all three are the
session endpoint reporting **its own** active profile's rights —
`CoreController.php:632`, gated `version_compare(..., '2.2', '>=')`. So
11.0.12 already serves it, and it is the same thing `CLAUDE.md` describes as
"v2.3 can describe the session it is already in and nothing else". It is not a
collection over the nine profiles.

**v3 is mostly a subtraction.** Eight routes are introduced at 3.0 — four
`LoginSession` routes in `SecurityController` (list my / a user's / all
sessions, revoke one) and four `{itemtype}/{id}/Infocom` routes in
`ManagementController` - **not** generic ones, see the correction below. Against those, **42 routes are removed** at 3.0, in
three controllers:

- **37 for `SoftwareLicense`** — 35 `bc*` back-compatibility routes in
  `AssetController` and 2 in `ComponentController`, all of them the
  `/SoftwareLicense` and `/Assets/SoftwareLicense` shapes left behind when the
  itemtype moved out from under Assets.
- **5 for `/Category`** in `KnowbaseController`, which is the
  `KnowbaseItemCategory` removal surfacing a second time — upstream's own
  comment at `src/Glpi/Knowbase/History/HistoryBuilder.php:477` reads "The
  `KnowbaseItemCategory` class no longer exists". That is the same change the
  table below records as taking the `knowbasecategory` right with it.

**None of the app's five v2.3 paths is among the removals**, and the app pins
v2.3 regardless, so none of this reaches it.

So the prize does not exist. **Phase 6 does not happen**: `glpi/legacy.rs`
stays, `glpi/refused.rs` stays, `mysql_async` stays, and the SELECT grant and
its quiet schema coupling stay. 12.0.1 is a version bump for this app, not a
simplification. See *What this does to phase 0* below.

Phase 1 exists to learn two things cheaply. Both came out of the tarball:

- **The hash** is the one above, usable directly — `glpi.nix` fetches the
  release `.tgz`, so the file hash applies and no placeholder-mismatch round
  trip is needed.
- **The PHP requirement**, which the plan listed as unknown:
  `src/autoload/constants.php` moves `GLPI_MIN_PHP` from **8.2 to 8.3** and

#### What this does to phase 0

Phase 0 names **two** reasons to move: the v3 simplification, and branch
longevity. Only the first was ever an open question, and it is now closed
negative. The second is untouched by anything above — it is a standing,
time-based reason that no finding about v3 could have affected.

So what the upgrade buys, concretely, is nothing in the code. Phase 6's entire
list fails to materialise: `legacy.rs` is not deleted, `refused.rs` is not
deleted, `mysql_async` is not dropped, the grant is not revoked, the schema
coupling in section 6 remains the one quiet failure mode, and v1's Basic-auth
sign-in remains a second authentication path. **Zero lines are deleted and
zero couplings removed.** The app on 12.0.1 has exactly the shape it has on
11.0.12.

Against that, the cost is small but entirely one-way:

- a forward-only `database:update`, whose rollback is a dump restore
- `right_taxonomy.json` regenerated, with one known diff (`knowbasecategory`)
- re-verifying sections 1-8 against a *running* 12 rather than against source

And the things that would have made it expensive are ruled out: **no PHP
move** (8.4.27 sits inside 12.0.1's 8.3-8.5), and **no client change** - v2.3
is still served so `mod.rs:229` still resolves, the pagination block is
byte-identical, the five right names are unchanged, the `changeProfile` guard
is still required, and v1 survives so the Rights page keeps its source.

#### What 12.0.1 says about branch support, which is phase 0's real input

`SECURITY.md`, shipped *in the 12.0.1 release*, is upstream's current
statement:

| branch | supported |
|---|---|
| 12.0.x | yes |
| 11.0.x | **yes** |
| < 11.0 | no |

Two things follow, and they pull in opposite directions:

- **There is no deadline today.** 11.0.x is a supported branch by upstream's
  own policy, which is the first actual source for section 0's "no security
  pressure" claim rather than an inference.
- **The retirement precedent is confirmed.** `< 11.0` is now unsupported, so
  10.0 has in fact been retired - the thing phase 0 cited 10.0.28 for. 11.0
  will follow eventually; nothing upstream states when.

But the policy adds a condition phase 0 did not account for:

> "Only the latest patch release of each supported branch is in scope. Reports
> against older patch versions are closed without review."

So deferring is not free - it converts into an obligation to **track 11.0.x
patches**. Being behind on 11.0.x patches puts this install out of scope as
surely as being on 10.0 would. That makes one unverified fact load-bearing for
the defer decision: **that 11.0.12 is still the latest 11.0.x patch.** It was
taken from the release listing, not checked against upstream as part of this
phase, and it is the thing to re-check whenever the question is revisited.

#### "A version bump" means for this app, not for GLPI

Worth stating plainly, because the shorthand above invites the wrong reading.
**12.0 is a substantial major release.** Its version number is earned by
removals and migrations rather than by additions:

- the `KnowbaseItemCategory` itemtype removed outright, and its right with it
- KB categories converted into articles under a new root article, on upgrade
- KB visibility changed to deny-by-default, on upgrade
- the XML-RPC API removed
- HL v2.0, v2.1 and v2.2 removed - 11.0.12 serves them, 12.0.1 does not

`Management` Infocom routes (not generic - see the correction below), and two
new RSQL operators. None of it lands in the three places
*this* app reaches outside v2.3, which is the whole of the finding above.

The reason a major release can be a near-no-op here is that the app consumes a
deliberately small and stable slice: five v2.3 paths, five v1 calls, and
twelve columns of one table. Everything 12.0 breaks sits outside that slice.
That is partly design and partly luck, and it should be re-established per
release rather than assumed to hold next time.

#### The sequencing question, and why it is not one

"Patch 11 first, or go straight to 12" looks like a choice and is not, for two
independent reasons:

- **There is no 11 patch to apply.** 11.0.12 is the head of its branch.
- **Patching would not be a prerequisite anyway.** Upstream: GLPI 11 carries
  migrations from 0.85 up, so major versions can be skipped entirely.

And patch-tracking is **not** a cost of deferring, as an earlier draft of this
file implied. `SECURITY.md` requires the latest patch of *whichever* branch
you are on, so the obligation is identical either way - 11.0.13 or 12.0.2. It
is a wash.

The one real asymmetry: **stay on 11.0 and the 12 migration still happens
eventually, on upstream's timetable instead of yours.** Nothing else about it
gets cheaper or dearer by waiting - except that 12.0.x accrues patches, which
makes waiting mildly *better*, not worse.

#### What 12.0 makes *possible*, which is a different question

Everything above measures 12.0 against the app's three *existing* gaps. That
is the question this file originally posed ("the prize"), and it is the wrong
one on its own: the app is in active development, so surface that lands
nowhere today can land somewhere later. The forward-looking inventory:

**New HL surface is eight routes.** That is the whole of it.

- **`LoginSession`** - `/LoginSession/My`, `/LoginSession/{users_id}`,
  `/LoginSession/All` (GET) and `/LoginSession/{uid}` (DELETE, revoke). Schema
  `x-version-introduced: 3.0.0`, backed by `User_SessionHistory`, carrying

- **`{itemtype}/{id}/Infocom`** x4 under Management - financial and

**But `LoginSession` is rights-gated, and expensively.** Its

```php

return ['WHERE' => ['_.users_id' => Session::getLoginUserID()]];
```

is close to superadmin and pulls hard against this app's read-only posture. That is a real trade, not a free gain, and it
should be priced before counting `LoginSession` as a reason to upgrade.

**Usable on existing endpoints**, which is cheaper than new routes:

- `morethan` / `lessthan` search operators for numeric fields
- `=istruthy=` / `=isnottruthy=` RSQL operators

Both allow server-side filtering where the app currently filters after the
fact.

**Adjacent to what this app is for**, though not API surface: automatic
actions gain `ERROR` and `ABORTED` statuses, a backoff-and-retry strategy,
and an `errored` property in the status checker naming the actions needing
manual intervention. "A scheduled job that quietly stopped working" is this
app's entire genre, and GLPI's own cron is a blind spot it does not currently
look at - zero references to the status checker anywhere in the tree.

**What no amount of future development gets on 12.0.1**, because it is not
modelled rather than merely unstable: `Profile_User`, `RefusedEquipment`, and

And if the app ever targets v3 rather than v2.3, `mod.rs:229`'s single literal
changes and the 42 routes removed at 3.0 need re-checking against whatever the

#### Correcting the rights claim made earlier in this file

The forward-looking section above said the service account "holds `agent`,
`computer`, `entity`, `profile`, `user` - not `config`". **That was wrong**,
and it conflated the five rights the app *needs* with the rights the account
actually *has*.

Read from the v2.3 session's `active_profile.rights`, profile `inv` (id 9,
central interface) holds **about 85 non-zero rights** - including
`config: 1`, and also `refusedequipment: 1` and `logs: 1`, rights for things
the API does not expose at all.

The conclusion survives but for a different reason. `READ` is 1 and `UPDATE`
is 2 (`src/autoload/constants.php:67-68`), so `config: 1` is **READ only**,
and `LoginSession`'s read condition requires `Config::$rightname` at
**UPDATE**. The escalation needed is therefore raising an existing right
rather than granting an absent one - smaller than stated, still meaningful.

#### `LoginSession/All` answers 200 whether or not it may

Worth recording, because it is this app's declared failure mode. Without
`config` UPDATE the route does not refuse - it returns **200** with the
caller's own sessions, because the rights condition degrades to a `WHERE`
clause rather than a denial:

```php
if (Session::haveRight(Config::$rightname, UPDATE)) { return true; }
return ['WHERE' => ['_.users_id' => Session::getLoginUserID()]];
```

A caller therefore cannot distinguish "no other sessions exist" from "I am not
allowed to see them". That is precisely what `CLAUDE.md` forbids rendering as
an empty list. The probe here is *consistent* with filtering but does not
prove it: `glpi_users_sessionhistory` is new in 12.0, so on a freshly migrated
copy the only session is the prober's own. The filtering is established from
the source and from the account holding `config` at READ, not from the
response.

**The rule, and it is implementable today.** v3's `session` carries
`active_profile.rights` natively - verified against the running instance,
`config = 1` - so a client on v3 can test its own authority without a
cross-version call:

```
GET /api.php/v3.0/session  ->  active_profile.rights.config
  & UPDATE (2)  ->  /Security/LoginSession/All is fleet-wide
  otherwise     ->  it is self-only; label it, never present it as fleet-wide
```

`READ` is 1 and `UPDATE` is 2, so the test is a single bit. No app code
changes for this today: the app pins v2.3 and calls no `LoginSession` route.
This is the rule to apply *if* it adopts one.

#### 12.0.1 gives the API a quiet failure mode, which section 6 denies

Section 6 calls the database schema "the only quiet failure" and contrasts it
with the API: "an API that drops a field names the field; SQL does not."
**That contrast is no longer true in 12.0.1.**

GLPI's HL schemas carry `x-rights-conditions`, and they degrade rather than
refuse - the same mechanism as `LoginSession` above, in two shapes:

- **Object-level**, filtering *rows*. `User` carries one: if
  `!Session::canViewAllEntities()`, a `LEFT JOIN` on `glpi_profiles_users`
  plus a `WHERE` on the session's active entities. Present in **both**
  versions, so this is standing behaviour and not an upgrade change.
- **Field-level**, dropping *columns* from the response. A field the caller
  may not read is simply absent - which the frontend renders as a blank cell,
  because every field is `Option` by design.

The field-level shape is **new in 12.0.1**. In `AdministrationController`:

| | 11.0.12 | 12.0.1 |
|---|---|---|
| `x-rights-conditions` | 4 | **16** |
| gated by `User::READAUTHENT` | 0 | **2** |
| gated by `Notification::canView()` | 0 | **10** |

The newly gated fields, read out of the source:

- `User.date_sync` and `Group.mfa_enforced` - `READAUTHENT`
- `Entity.admin_email`, `admin_email_name`, `from_email`, `from_email_name`,
  `noreply_email`, `noreply_email_name`, `replyto_email`, `replyto_email_name`,
  `notification_subject_tag`, `mailing_signature` - `Notification::canView()`

**This app reads none of them** - checked across `backend/` and `frontend/`,
zero occurrences of any field in that list. So the upgrade has no impact here
and nothing needs fixing in the code.

What does need fixing is the claim. Section 6's "the only quiet failure" and
its reasoning that the API always names what it drops should be read as
**true for 11.0.12 and false for 12.0.1**. On 12.0.1 the correct statement is
that there are two quiet failure modes - the SQL schema, and any HL field
carrying a `read` rights condition - and that the app currently happens to
touch neither.

That last clause is the fragile one. It holds because of which fields the app
reads today, not because of anything structural, so it is worth re-checking
whenever the app starts reading a new field from `User` or `Entity`.

### Built: the API's quiet failure made loud

`backend/src/glpi/schema_check.rs`, plus `GET /api/field-gaps`. Written
because the section above found that 12.0.1 gives the API a quiet failure mode
and the app had no way to see it.

**The mechanism.** GLPI serves its own OpenAPI document at
`/api.php/v2.3/doc.json` - `security_level: SECURITY_NONE`, introduced at API
2.0, so it exists on the deployed 11.0.12 too. The document is generated from
the schema declarations and is **not** filtered by the caller's rights, while
the response **is**. The difference between the two is the suppression, and it
can be named.

**The design decisions that matter:**

- **`writeOnly` is excluded.** `User.password` and `password2` are declared
  and never returned to anybody, so counting them would be a permanent false
  positive on every call. Only ten such properties exist across all 330
  schemas in 12.0.1's document, so the exclusion is precise, not a heuristic.
- **Fields are unioned across rows**, not read off row zero. GLPI can omit a
  null field on one record and send it on another, and keying off the first
  row would invent findings.
- **No rows means `Unknown`, not `Ok`.** An empty collection tells you nothing
  about suppression, and this is the same rule the rest of the app applies to
  an empty list versus a failed fetch. Without it an empty response would
  report a clean bill of health for every field.
- **Two gap kinds.** `suppressed` (declared, readable, absent) is a rights
  finding. `undeclared` (arrived, never declared) is upgrade drift - the app's
  understanding of an endpoint being behind the server's.
- `compare` is pure over already-fetched values, so the judgement is testable
  without a GLPI. Same split `posture` uses. Eight unit tests.

**Measured against both instances, same binary.** This is the result that
shows it is calibrated rather than merely green:

| schema | 11.0.12 | 12.0.1 |
|---|---|---|
| `Agent` | ok 27/27 | ok 27/27 |
| `Computer` | ok 30/30 | ok 30/30 |
| `Entity` | ok 37/37 | ok 37/37 |
| `User` | **ok 29/29** | **attention 30/29 - `date_sync`** |
| `Session` | ok 13/13 | ok 13/13 |

Silent on the deployed version, and firing precisely on what 12.0.1 adds:
12.0.1 *declares* `date_sync` and then withholds it from an account without
`User::READAUTHENT` (2048), while 11.0.12 never declared it at all. One true
positive, no false positives, on real instances.

**What it does not do.** Top-level fields only - a suppressed key inside a
nested object is invisible to it. And it reports that the schema promised a
field the response did not carry, never *why*: a field withheld by rights and
a field GLPI stopped sending are both simply absent. The endpoint says so in
its own `cannot_check` string rather than leaving the reader to assume reach
it does not have.

`doc.json` is ~4.6 MB on 12.0.1 and is fetched per request, so this is a
diagnostic endpoint and not something a page should poll. It is deliberately
not cached: a cached copy goes stale exactly across an upgrade, which is the
one moment the answer has to be current.

**Not yet wired into the UI.** The natural home is the Rights page's Api tab,
which already exists to state what the app cannot see. The backend answer is
complete and verified; the tab is not written.

### Phase 4, part one — the "document" advisory, chased

`database:update` printed *"Rights have been given for document, you should
review ACLs after update"*. What it did, read from

```php
// Add SEEPRIVATE right (8192) to profiles that have UPDATE right on documents
// This preserves existing behavior where technicians can see all documents
$migration->giveRight('document', 8192, ['document' => UPDATE]);
```

It adds an `is_private` column to `glpi_documents_items`, then grants

```
11.0.12   {1:0, 2:33, 3:127,  4:255,  5:0, 6:127,  7:127,  8:33, 9:33}
```

### The option phase 6 missed: extend the API instead of waiting for it

Phase 6 was written as conditional on upstream - "only if phase 3 found v3
covers what v1 and SQL are used for". v3 did not, so the whole section was
filed as dead. **That framing had a gap: GLPI's High-Level API is extensible,
and nothing here had checked.**

#### The mechanism

`Router.php:274-286`, immediately after registering its own eleven
controllers:

```php
// Register controllers from plugins
if (isset($PLUGIN_HOOKS[Hooks::API_CONTROLLERS])) {
    foreach ($PLUGIN_HOOKS[Hooks::API_CONTROLLERS] as $controllers) {
        foreach ($controllers as $controller) {
            if (is_subclass_of($controller, AbstractController::class, true)) {
                self::$instance->registerController(new $controller());
            }
        }
    }
}
```

Two hooks: `api_controllers` and `api_middleware`
(`src/Glpi/Plugin/Hooks.php:1123` and `:1132`). A plugin names controller
classes; the Router instantiates and registers them exactly as it does its
own. A controller declares its data through `getRawKnownSchemas()` - the same
entry point `AssetController` uses - so a plugin schema inherits the entire HL
machinery: the `start`/`limit` walk with `Content-Range`, RSQL filtering,
`x-rights-conditions`, an entry in `doc.json`, GraphQL resolution.

#### Which gaps this could close

All three things this app reaches outside v2.3 for are ordinary itemtypes with
database tables, not computed PHP:

| gap | today | as a plugin schema |
|---|---|---|
| profile rights across profiles | v1 `ProfileRight` | an HL schema over `ProfileRight` |
| who may use which profile, where | v1 `Profile_User` | an HL schema over `Profile_User` |
| refused submissions | **a SQL grant** | an HL schema over `RefusedEquipment` |

`RefusedEquipment` is the one worth doing. It is
`class RefusedEquipment extends CommonDBTM` with
`public static string $rightname = 'refusedequipment'`, and - checked against
the live session, not assumed - **this app's account already holds
`refusedequipment` at READ**. So exposing it needs no new privilege at all.

Closing that one would let the app delete `glpi/refused.rs`, drop
`mysql_async`, and **revoke the SELECT grant** - which removes the schema
coupling that section 6 calls the only quiet failure mode, and removes the
second credential with it.

The two profile gaps are not worth it. v1 already answers them, costs nothing
to maintain, and survived the major upgrade intact.

#### Packaging: cheaper than expected

The obstacle looked like the immutable store path - the release's own
`plugins/` is inside `/nix/store` and cannot be written to. It is not an
obstacle. `SystemConfigurator.php:94` defines the production default as:

```php
'GLPI_PLUGINS_DIRECTORIES' => [
    '{GLPI_MARKETPLACE_DIR}',
    $this->root_dir . '/plugins',
],
```

`{GLPI_MARKETPLACE_DIR}` is an inheritance placeholder, and `glpi.nix:149`
already sets `GLPI_MARKETPLACE_DIR` to `${cfg.stateDir}/marketplace` -
`/var/lib/glpi/marketplace`, glpi-owned and writable. It is also **first** in
the search order, ahead of the release's own directory.

So a plugin drops into `/var/lib/glpi/marketplace/<key>/` with **no change to
`glpi.nix`, no derivation patch, and no new environment variable**. The
`GLPI_PLUGINS_DIRECTORIES` constant can also be overridden from the
environment (`SystemConfigurator.php:190` defines any `GLPI_*` constant from
`getenv`), but there is no need to.

#### The honest cost

This does not remove a trade, it relocates one:

- **Today:** two APIs and a SQL grant, and upstream's instability is
  upstream's problem. v1 is "closely tied to the GLPI source code" but GLPI
  keeps it working.
- **With a plugin:** one API, no grant, no second credential - and PHP you
  maintain against `AbstractController`, `Doc\Schema` and `ResourceAccessor`,
  which are internals with no stability promise either. A plugin also declares
  GLPI version compatibility and is disabled when the install moves outside
  its range, so an upgrade can silently take the refused view offline.
- `CLAUDE.md` currently records "no plugins are installed" and the release's
  `plugins/` is empty. That stops being true, and the deployment grows a
  component.

#### Proved, on the throwaway instance

A probe plugin - `refprobe`, one read-only route, no tables, no UI - was
written and installed into `/var/lib/glpi-test/marketplace/refprobe` on the
12.0.1 test instance. **It works.** The inference is now an observation:

```
GET /api.php/v2.3/Refprobe/RefusedEquipment   ->  200  []
Content-Range                                 ->  0--1/0
doc.json schema count                         ->  331   (was 330)
  components.schemas.RefusedEquipment         ->  present, all 12 properties
  paths./Refprobe/RefusedEquipment            ->  present
```

The empty array is the correct answer - this install has refused nothing -
and the point was never the rows. What is established is that a
plugin-declared schema **reaches the OpenAPI document and the search
machinery**, carries a `Content-Range`, and is served from a writable state
directory with no change to `glpi.nix`, no derivation patch and no new
environment variable.

So **phase 6 is reachable**: `glpi/refused.rs`, `mysql_async` and the SELECT
grant could all go, using a right (`refusedequipment`) this account already
holds.

#### Two costs, also observed rather than reasoned

Both were hit while building the probe, which is precisely what the throwaway
was for.

- **A malformed plugin route takes down the WHOLE High-Level API.**
  `RoutePath::getRouteVersion()` is
  `getAttributes(RouteVersion::class)[0]->newInstance()` with no guard, and
  `matchesAPIVersion()` calls it from an `array_filter()` over every
  registered route. A route missing `#[RouteVersion]` therefore throws while
  GLPI is merely *enumerating* routes: `/api.php` and every endpoint returned
  500, with nothing in the response naming the plugin. The cause was only
  visible in `files/_log/php-errors.log`. The blast radius of a plugin defect
  is total, not confined to the feature it adds.
- **`plugin_<key>_install` is mandatory**, even for a plugin that owns
  nothing. `Plugin.php:1245` looks it up and reports "function is missing"
  rather than treating absence as nothing-to-do. Same for `_uninstall`.

Also worth recording: `plugin:list` shows *registered* plugins, not
discovered ones - it was empty until `plugin:install` ran, which is the step
that scans the directories.

#### Still not exercised

Version compatibility. `plugin_version_refprobe()` declares
`requirements.glpi = {min: 12.0, max: 13.0}` and GLPI accepted it, but no
upgrade has been run against a plugin to watch it be disabled at the
boundary. That is the failure this would have to be trusted not to cause
quietly, and it remains untested.

### A third quiet failure: an RSQL filter that is silently ignored

Found as a control while proving the plugin point, and more consequential
than the thing it was controlling for.

**GLPI drops a filter term naming a field it does not know, and runs the
query without it.** `Search.php:443`:

```php
$other_invalid_filters = array_filter($filter_result->getInvalidFilters(),
    static fn($error) => $error !== Error::UNKNOWN_PROPERTY);

// Fail the request if any of the filters are invalid
if ($schema_resolver === null && $other_invalid_filters !== []) {
    throw new RSQLException(...);
}
```

`UNKNOWN_PROPERTY` is deliberately lifted out of the set that throws. An
unknown **operator** and a mapped property raise `RSQLException` and name the
term; an unknown **field** does not. Upstream's own comment on that branch
overstates the code beneath it.

Measured on the running 12.0.1, counting rows on `Assets/Computer`:

| filter | rows | |
|---|---|---|
| *(none)* | 1 | |
| `name=="nixos"` | 1 | applied |
| `name=="no-such-machine"` | 0 | applied |
| `no_such_field=="x"` | **1** | **ignored** |
| `is_deletedX==0` | **1** | **ignored** |

#### Why this is a section 6 problem

Section 6 named one quiet failure - a renamed database column. The
*Correcting section 6* note above added a second - a field suppressed by
`x-rights-conditions`. This is a third, and it is the nastiest, because it
fails **open** rather than empty:

- a suppressed field yields a blank cell
- a renamed SQL column yields a blank cell
- **an ignored filter yields MORE DATA THAN ASKED FOR**, with a 200

A filter relied on for correctness rather than speed therefore cannot be
trusted on its own. `ac1e2a9` filtered soft-deleted machines out server-side
and trusted it; rename `is_deleted` upstream and every trashed machine
returns, flagged `orphaned`, silently. `de2de36` fixes that by re-checking
locally in both readers and logging when GLPI evidently ignored the term.

**The rule this leaves:** a server-side filter in this app is an
optimisation, never a guarantee. Anything excluded for correctness is
excluded again locally.

#### It also corrects the DB page

The api-read tab states that RSQL's three error kinds - unknown property,
unknown operator, mapped property - "all name the offending term rather than
failing the whole call silently, which is the one respect in which this is
friendlier than the database". **Two of the three do.** Unknown property is
exactly the silent case, and it is the one a field rename produces.
